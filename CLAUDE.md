# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`file_saver_ffi` is a Flutter plugin (published on pub.dev) for saving bytes, local files, and network downloads to gallery/device storage or a user-picked directory, with progress streaming, cancellation, conflict resolution, and streaming write sessions. Platforms: Android (JNI → Kotlin), iOS/macOS (FFI → Swift, shared `darwin/` source), Windows/Linux (pure Dart + `dart:io`), Web (`package:web` / `dart:js_interop`). Dart tests live in `test/` (`flutter test`), Kotlin tests in `android/src/test` (Robolectric, with a fake MediaStore provider in `testing/`), Swift tests in `darwin/file_saver_ffi/Tests` (XCTest, `swift test` on macOS). The `example/` app is the manual test harness (its `widget_test.dart` is the default Flutter template and is stale). On-device tests of the Android JNI bridge live in `example/integration_test/android_test.dart`, and of the Darwin FFI bridge on iOS in `ios_test.dart`; CI doesn't run them. Every fix ships with tests for what it changes.

```bash
flutter pub get                      # root package
flutter analyze                      # flutter_lints plus strict modes and async lints (analysis_options.yaml); CI fails on any info
dart format lib tool

cd example && flutter run -d <device>   # manual testing on a target platform

# Kotlin unit tests (JUnit + Robolectric, android/src/test). Needs the example's
# Gradle project, generated by any example build or `flutter build apk --config-only`.
cd example/android && ./gradlew :file_saver_ffi:testDebugUnitTest

cd example && flutter test integration_test/android_test.dart -d <device>

# Web tests (test/platforms/web, @TestOn('browser'); the VM run skips them)
flutter test --platform chrome test/platforms/web

# Swift unit tests (XCTest) of the shared Darwin source, on the macOS host
cd darwin/file_saver_ffi && swift test

# On-device tests of the Darwin FFI bridge (iOS simulator or device). The
# first Photos test opens the Photos permission dialog: answer "Allow Full
# Access" after it has been open for 2 s (by hand, or with agent-device).

cd example && flutter test integration_test/ios_test.dart -d <device>

# Regenerate Darwin FFI bindings after editing the C header (CI fails if the
# committed bindings differ from what this generates)
dart run tool/ffigen.dart

# Regenerate the Kotlin and Swift copies of the cross-language contracts
# (Contracts.g.kt, Contracts.g.swift) after changing one of the Dart
# declarations listed in tool/contracts.dart (test/tool/contracts_test.dart
# fails if they differ)
dart run tool/contracts.dart

# Check that R8 kept every class and member the JNI bindings look up (CI runs
# this on the release APK of every Android change)
(cd example && flutter build apk --release)
dart run tool/check_jni_keeps.dart example/build/app/outputs/flutter-apk/app-release.apk

# Regenerate Android JNI bindings after changing the public Kotlin API of
# FileSaver or ProgressCallback. Compiles the plugin's Kotlin via
# example/android/gradlew (gradlew.bat on Windows) first, so the example must

dart run tool/jnigen.dart
```

Never hand-edit `lib/src/platforms/{android,darwin}/bindings.g.dart`. `android/proguard-rules.pro` is merged into every consuming app, so it only keeps what the bindings look up by name. When the bindings gain a type in a signature (a new class, interface or Kotlin synthetic), keep its name there, or `check_jni_keeps.dart` fails. Swift formatting config is `darwin/.swift-format`; Kotlin follows ktlint style.

## Architecture

### Dart layer
- `lib/file_saver_ffi.dart` — the `FileSaver` static facade, the only public entry point. It dispatches on the sealed `SaveInput` (bytes / file / network) to `FileSaverPlatform.instance`.
- `lib/src/platform_interface/file_saver_platform.dart` — abstract contract, public through `lib/platform_interface.dart` so apps can fake it in tests. Each platform class is wired up via `dartPluginClass`/`pluginClass` in `pubspec.yaml` and sets `FileSaverPlatform.instance` in `registerWith()`. The registrant imports `lib/file_saver_ffi.dart`, which therefore exports the platform classes (by name, with `show`).
- Conditional exports keep web and IO code apart: `io_platforms.dart` (real Android/Darwin/Windows/Linux classes) vs. `io_stub.dart` on web, and `web/file_saver_web.dart` vs. `web_stub.dart` on IO. **When you add or rename a platform class or a required interface method, update the matching stub and the `show` list too.**
- Every operation returns `Stream<SaveProgress>` (Started → Update* → Complete | Error | Cancelled). `saveAsync` and similar wrappers sit on top of these streams. The streams are single-subscription: build a new one with `singleSubscription` of `shared/single_subscription.dart`, not `Stream.multi`, which would run the save once per listener.
- `PathLocation` (a raw filesystem path) skips native code on every IO platform and goes through `shared/path_location_writer.dart`. Windows and Linux save through it too: it is the only `dart:io` save path, and it writes through the `IOWriteSession` of `shared/io_file_saver_sink.dart`.
- Windows and Linux share `shared/desktop_file_saver.dart`. Subclasses implement only `resolveDirectory` (Known Folder GUIDs on Windows, XDG dirs on Linux) and `launchFile` (`ShellExecuteExW` via `windows/windows_shell.dart` on Windows, `xdg-open` on Linux). `launchFile` must never pass the path through a shell such as `cmd`.
- Streaming write sessions (`openWrite`/`openWriteAs`) return a `FileSaverSink`. Every platform's sink is `shared/session_file_saver_sink.dart`, which owns the lifecycle (ordering, back-pressure, errors, cancel, the `Finalizer`); each platform's `*_file_saver_sink.dart` only implements a `WriteSession` (JNI, FFI, `dart:io`, or File System Access / an in-memory buffer on web).

### Native bridges
- **Darwin**: Dart calls the C ABI declared in `darwin/file_saver_ffi/Sources/file_saver_ffi/FFI/file_saver_ffi.h`, which is implemented in Swift (`FFI/FileSaverFFI.swift`). Progress goes back through a Dart `NativePort`, posted by the small C target `Sources/FileSaverDartApi` (`Dart_PostCObject` resolved from `NativeApi.initializeApiDLData`). Messages are arrays: `[0]` started, `[1, bytesWritten, totalBytes]` progress (`totalBytes` is null if unknown), `[2, code, msg]` error, `[3, uri]` success, `[4]` cancelled. Both bridges send cancelled (4) only after a cancel, once the save has stopped and removed what it wrote, and the Dart `onCancel` waits for it. `ProgressReporter` throttles progress to steps of 1% of the size or 100 ms, and sends the count it held back before success. The library loads via `DynamicLibrary.process()`. A `DarwinFileSaverSink` also has a `NativeFinalizer` (`file_saver_finalize_write`), which cancels its session when the sink's isolate goes away without closing it; it runs without an isolate, so it must never post to Dart. The native functions copy their string arguments before returning, and take ownership of byte buffers (Dart allocates them with `malloc`, Swift frees them). Both SwiftPM (`Package.swift`) and CocoaPods (`file_saver_ffi.podspec`) are supported, so keep both working. Both ship the privacy manifest `Sources/file_saver_ffi/Resources/PrivacyInfo.xcprivacy` (CI checks that built apps bundle it with `tool/check_privacy_manifest.sh`); when the Swift code starts calling another [required reason API](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api), declare it there.
- **Android**: `FileSaverAndroid` calls the jnigen-generated wrapper around `com.iamv4g.file_saver_ffi.FileSaver` (Kotlin, coroutines). Progress arrives through a Dart-implemented `ProgressCallback` interface with the same event types; a progress event (1) carries the bytes written as `progress` and the file size, if known, as `data`, throttled by `ProgressThrottle` like the Darwin `ProgressReporter`. `FileSaverFfiPlugin` exists only to give `FileSaver` its application context and Activity (for permission prompts). The Dart-side `FileSaver` is created lazily because the JVM isn't ready during plugin registration.
- Android saves every file type with one `EntrySaver`, into the entry of a `SaveEntryFactory` (MediaStore or SAF). Darwin saves every file type with one `SaveEngine` (`Core/`), and `PhotosHelper.createAsset` adds images and videos to the Photos Library. Each side has conflict resolvers per storage backend (MediaStore scoped/legacy and SAF on Android; Photos and FileManager on Darwin).

### Cross-language contracts
Dart declares them; `tool/contracts.dart` generates their Kotlin (`models/Contracts.g.kt`) and Swift (`Models/Contracts.g.swift`) copies, which are never hand-edited. Each Dart declaration has a comment saying so.
- Dart sends `ConflictResolution.index` and the platform `SaveLocation` enum `.index` across the bridge as plain ints. Kotlin and Swift get enums of the same order (`fromInt` in `ConflictResolution.kt`/`.swift` and `SaveLocation.kt`/`.swift` adds the fallback for an unknown index, and the macOS `directoryURL`).
- Native code sends events as `NativeEventType` indices (`EventType` in Kotlin and Swift) and errors with the `FileSaverErrorCode` strings (`ErrorCode`), which map to the Dart exceptions in `lib/src/exceptions/file_saver_exceptions.dart`. `test/contracts/native_contract_test.dart` fails if native code writes one of them as a literal.
- Adding a native function means changing the C header and Swift `@_cdecl`, then regenerating (`tool/ffigen.dart` binds every function the header declares). On Android it means changing Kotlin, then running jnigen (only the classes listed in `tool/jnigen.dart` are exposed).

### Web
The download strategy depends on the API: `saveNetwork` without headers uses an `<a download>` anchor, with headers it uses `fetch` → Blob, and `saveAs`/`openWriteAs` use the File System Access API on Chromium with a fallback to a regular download. `WEB_LIMITATIONS.md` documents what users see from this, so update it when web behaviour changes.

## Conventions
- Commit messages use Conventional Commits with a platform scope, e.g. `feat(darwin): …`, `refactor(android): …`, `chore(example): …`.
- User-facing changes go in `CHANGELOG.md`. Version bumps update `pubspec.yaml` (the README setup sections should match the platform minimums).
- CI (`.github/workflows/ci.yml`) runs only the platform jobs a pull request needs. `tool/ci_changes.sh` maps the changed paths to platforms, and unknown or shared paths run everything. Pushes to `main`, manual runs and the release run everything. A push to a PR or to `main` cancels the run it supersedes, so merging several PRs in a row ends with one full run, of the newest commit. The ruleset requires only the `CI result` job. Its `tool/ci_result.sh` passes only if every job succeeded, or was skipped because the change doesn't need it (per the `changes` outputs); anything else fails, including a job GitHub cancelled for want of a runner. When you add a platform folder or a CI job, update `tool/ci_changes.sh`, the `needs` list of `CI result`, and, for a job that runs only for some changes, the jobs `tool/ci_result.sh` lets be skipped. Check a mapping locally with `git diff --name-only origin/main... | bash tool/ci_changes.sh`.
- Releases are published to pub.dev by `.github/workflows/publish.yml` when a `v<version>` tag is pushed. The tag must point to a commit on `main` whose `pubspec.yaml` version matches and whose `CHANGELOG.md` has a `## <version>` section. Never run `flutter pub publish` locally.
